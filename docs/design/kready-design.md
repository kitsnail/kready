# kready：Kubernetes 集群就绪检查工具（大框架设计）

> 参照 Intel Cluster Ready 的思路：一条命令检查 Kubernetes 集群是否"就绪"（Ready）。
> 本文只确定大框架，细节（具体检查项、参数、配置格式等）放到后续逐一讨论。

## 一、项目宗旨

**面向一线运维工程师，简单易懂，方便快捷。**

由此派生的四条硬约束，所有设计决策都以此为准：

1. **简单**：一个命令就能用，不需要先学配置语言；输出用大白话，不用内部术语。
2. **易懂**：结论在最前面；每个失败项都说清楚"是什么问题、影响什么、怎么修"。
3. **快捷**：默认模式 30 秒内出结果，不需要额外部署任何东西。
4. **安全**：默认只读，不改变集群状态，可以放心在生产环境执行。

## 二、目标用户与典型场景

**用户**：一线运维工程师（熟悉 kubectl 基本操作，不一定熟悉 K8s 内部原理）。

| 场景 | 运维想知道的问题 | kready 的回答 |
|---|---|---|
| 新集群交付 | 这个集群能不能交给业务用？ | 正常 / 异常，以及异常的原因与 WARN 提醒 |
| 日常巡检 | 集群现在有没有问题？ | 一屏看完，有问题的项目排在前面 |
| 升级前评估 | 升级会不会出事？ | 版本是否兼容、有无阻塞升级的隐患 |
| 故障排查 | 哪个组件出问题了？ | 快速定位到具体组件和修复命令 |
| 流水线门禁 | 部署后能否自动判定成功？ | 通过返回 0，否则返回非 0 |

## 三、命令设计（大框架）

采用**少量、动词化、默认即可用**的命令结构：

```
kready check            # 一键检查（最常用，默认模式）
kready check --full     # 完整检查（包含更多项，耗时更长）
kready node             # 节点环境预检（可不依赖集群）
kready fix-hint <项目>  # 查看某个失败项的详细修复说明
kready version          # 版本信息
```

设计要点：

- **零配置**：直接运行 `kready check` 即可，不要求用户写任何文件。
- **可选场景**：通过内置场景名选择检查范围（如 `--scene gpu`），而不是让用户编写 YAML。
- **作为 kubectl 插件使用**：支持 `kubectl ready check` 的调用方式，降低记忆成本。

## 四、检查内容的组织方式

按运维习惯的 **"从底到上" 五大类** 组织，而不是按内部技术分层：

1. **节点**：操作系统、内核参数、容器运行时、时间同步、磁盘空间等
2. **控制面**：API Server、etcd、调度器等是否健康，证书是否快过期
3. **网络与 DNS**：网络插件是否正常、DNS 能否解析、服务能否访问
4. **存储**：存储类是否可用、默认存储类是否设置
5. **组件与业务**：常用组件（监控、Ingress 等）是否正常、必要配置是否齐全

每一类内部的具体检查项在后续讨论中逐一确定。

## 五、运行模式

| 模式 | 说明 | 耗时目标 | 是否需要额外部署 |
|---|---|---|---|
| 默认模式 | 只读访问 API，检查常见项 | < 30 秒 | 否 |
| 完整模式（`--full`） | 增加更多检查项 | 数分钟内 | 否 |
| 节点模式（`--nodes`） | 登录或临时进入节点采集本地信息，用完即清理 | 视节点数而定 | 临时，自动清理 |
| 端到端冒烟（可选，默认关闭） | 临时创建资源验证 DNS、Pod 通信、存储绑定等 | 数分钟内 | 临时，自动清理 |

原则：**默认模式不做任何写操作，也不需要在集群里长期安装组件。**

## 六、输出设计（最重要的体验）

终端输出采用**结论先行、问题优先**的结构：

```
kready 检查结果：异常  （2 个 FAIL，1 个 WARN）  耗时 18 秒

【需要处理】
  ✗ CoreDNS 副本数不足：只有 1 个在运行，应为 2 个
    影响：集群内域名解析可能不稳定
    处理：kubectl -n kube-system describe deploy coredns（只读查看）

  ✗ 节点 worker-03 未开启网桥过滤
    影响：该节点上的容器网络可能不通
    处理：modprobe br_netfilter（会改配置）

【建议关注】
  ⚠ 集群没有默认存储类，新建 PVC 时需指定存储类

【正常】 共 42 项通过（跳过 3 项）
```

输出约定：

- **颜色与符号**：✗ 红色（FAIL）、⚠ 黄色（WARN）、✓ 绿色（正常）；支持关闭颜色，便于日志留存。
- **中文输出**：默认中文，所有提示用运维能直接看懂的语言。
- **三要素**：每个问题都包含"问题 / 影响 / 处理"，缺一不可。
- **可复制**：处理命令单独成行，可直接复制执行。
- **风险标注**：处理命令标明风险等级（只读查看 / 需重启 / 会改配置），让运维心里有数。
- **其他格式**：`--output json`（给脚本和平台用）、`--output html`（给留档和汇报用），非默认。

## 七、结论与退出码

- 结论只有两种：**正常**（无 FAIL 与 ERROR）与 **异常**（存在 FAIL 或 ERROR）。WARN 不改变结论，但单独列出，供运维判断。
- 退出码：`0` 正常，`1` 异常，`2` 工具自身出错（如无法连接集群、无适用规则）。
- 检查失败（如某项超时）只会标记该项（ERROR），不会影响其他项的结果，并明确提示"此项未能检查"。

## 八、安全原则

- **默认只读**：只使用查询类接口，运维只需要只读权限即可使用。
- **不泄露敏感信息**：不输出 Secret 内容、私钥、访问凭据；报告中对内网地址和镜像仓库凭据做脱敏。
- **临时即清理**：节点采集、端到端冒烟等需要临时资源的功能，结束后必须自动清理，并在输出中确认已清理。
- **权限最小化**：需要高权限的功能（节点采集、端到端冒烟）必须单独开关，默认关闭。

## 九、技术方向（初步，待定）

- **实现语言**：Go（与 Kubernetes 生态一致，单二进制、易分发，方便运维直接下载使用）。
- **分发方式**：单个可执行文件；同时支持作为 kubectl 插件安装。
- **离线可用**：内置检查规则，不依赖外网；支持内网镜像仓库环境。
- **多集群**：支持通过 `--context` 指定集群，后续支持批量检查多个集群并汇总。

## 十、实施路线（大框架）

| 阶段 | 目标 | 核心内容 |
|---|---|---|
| 第一阶段：MVP | 能用、好懂 | `kready check` 默认模式；常用检查项；中文终端输出；修复命令；退出码 |
| 第二阶段：补齐 | 覆盖常见场景 | `kready node` 节点预检；`--full` 完整模式；`fix-hint` 详细说明；场景选择 |
| 第三阶段：便利 | 日常化 | 与上次结果对比，只显示变化；HTML 报告；可集成到流水线 |
| 第四阶段：扩展 | 按需生长 | 端到端冒烟；多集群汇总；自定义场景；社区场景包（如 GPU、MLOps） |

## 十一、决策记录与待讨论问题

### 已决定（见 ADR 与各设计文档）

1. **规则包选择**：按观测到的 kubelet 版本选包，不做基线哈希校验。
2. **节点采集**：通过 SSH 只读采集，账号保持 root（ADR 0001）。
3. **结论与分级**：结论为"正常 / 异常"；增加 WARN 级别，不改变结论。
4. **信息价值原则**：输出须有直接价值、辅助决策，尽量保证信息有效、可靠；无法可靠判定的项只输出 INFO，不为凑数而判定。
5. **SYS-04**（metrics-server 副本数）：`mode: info`，不判定。

### 待讨论（需 B 类确认后才能定稿）

1. **节点检查是否独立成节点模式**：NODE 规则是否归入 `--nodes`，默认 `check` 不做 SSH。
2. **问题说明字段**：`impact`（影响）、`hint`（处理）的字段名、是否必填、缺失时的处理方式；风险等级的取值。
3. **WARN 判定依据**：哪些规则用 `severity: warn`，需要逐条定义。
4. **具体检查项清单与阈值**（按五大类逐项确定）。
5. **场景包的划分与命名**。
6. **自定义规则的最低限度形式**。
7. **中文提示文案与术语表**。
8. **报告留存位置与历史对比方式**。
9. **与 CI/CD、GitOps 流程的对接方式**。
10. **命名确定**：`kready` 是否沿用。
