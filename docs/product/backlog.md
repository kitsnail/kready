# 需求清单（backlog）

> 维护者：人（产品经理）。Agent 仅按 `docs/product/README.md`「字段级权限」写入（D-011）。
> 排列：按优先级，从高到低。每条需求使用 `REQ-nnn` 编号，编号不复用。

## 条目模板

复制下面的模板，按编号顺序追加到文件末尾。

```markdown
### REQ-000 <一句话标题>

- 状态：草稿 / 待开始 / 进行中 / 待验收 / 已验收 / 已取消
- 优先级：高 / 中 / 低
- 背景：为什么要做（一两句）
- 期望结果：用户能做到什么
- 验收标准：见 `acceptance.md` 中的 REQ-000
- 关联：规则 ID、PR、CHANGELOG 条目（由 Agent 回填）
```

## 需求列表

### REQ-001 GPU 节点自洽检查：device plugin、可分配 GPU 数、节点标签与污点

- 状态：草稿
- 优先级：中
- 背景：GPU 节点交付后，需确认 Kubernetes 能正确识别并分配 GPU。这些检查只依赖集群自身数据，不依赖外部版本标准。
- 期望结果：运维执行 `kready check` 后，能看到 GPU 节点的调度前提是否满足。
- 验收标准：见 `acceptance.md` 中的 REQ-001
- 范围补充（人确认）：标签与资源名采用 NVIDIA 标准化名称（`nvidia.com/*`），不使用自定义名；结果按 `nvidia.com/gpu.product` 机型分组输出。
- 关联：待 D-012（新规则包 `rules/gpu/`，取数方式为只读 Kubernetes API）；CHANGELOG 待回填

### REQ-002 GPU 节点存在性检查：驱动加载与 GPU 数量

- 状态：草稿
- 优先级：中
- 背景：驱动未加载或 GPU 数量与物理卡数不一致，会导致 GPU 工作负载不可用。这类检查只需确认存在性与数量，不需要版本标准。
- 期望结果：运维能看到驱动是否加载、节点上可分配的 GPU 数是否与物理卡数一致。
- 验收标准：见 `acceptance.md` 中的 REQ-002
- 范围补充（人确认）：物理卡数同时采用两个来源交叉验证：GFD 标签 `nvidia.com/gpu.count` 与节点硬件信息（具体来源待 D-012 确认）；两者不一致时判异常。
- 关联：待 D-012
